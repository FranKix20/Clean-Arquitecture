Clean Architecture Por qué importa cómo organizas tu código

Una guía práctica sobre el patrón de arquitectura que separa responsabilidades, facilita el mantenimiento y hace que tu código escale sin caos.

El problema

¿Por qué el código se vuelve un desastre?

Sin estructura definida, los proyectos crecen de forma caótica.
Todo termina mezclado con todo.

🍝
Código Espagueti
La lógica de negocio, la base de datos y el HTTP viven en el mismo archivo.
😰
Miedo a tocar
Cambiar una cosa rompe otras tres. Nadie sabe exactamente por qué.
🧪
Imposible testear
No puedes probar la lógica sin levantar el servidor completo.
🔒
Atado al framework
Migrar de Express a Fastify implica reescribir la app entera.
La solución

¿Qué es Clean Architecture?

Es un conjunto de principios que organiza el código en capas con responsabilidad única, donde cada capa solo conoce a la capa inmediatamente inferior. Popularizado por Robert C. Martin (Uncle Bob).

01
Separación de responsabilidades
Cada módulo hace una sola cosa y la hace bien. No más, no menos.
02
Independencia del framework
La lógica de negocio no sabe si usas Express, Fastify o cualquier otro.
03
Dependencias hacia adentro
Las capas externas conocen a las internas. Nunca al revés.
04
Testeable por naturaleza
Puedes probar la lógica de negocio sin HTTP, sin BD, sin nada externo.
Anatomía

Las capas del proyecto

Cada archivo tiene un lugar claro. Cada lugar tiene una única razón para cambiar.

Routes
Define qué URL responde a qué. Sin lógica propia.
welcome.routes.ts
Controllers
Recibe la request, extrae datos, llama al service, responde.
welcome.controller.ts
Services
Lógica de negocio pura. No sabe nada de HTTP.
welcome.service.ts
Models
Tipos e interfaces que definen el dominio de la aplicación.
welcome.model.ts
Middlewares
Interceptan la request antes de llegar al controller.
logger.middleware.ts
Utils
Herramientas reutilizables que no pertenecen a ninguna capa específica.
logger.ts
En la práctica

El flujo de una request

Cuando el usuario hace GET /api/message, así viaja la información por las capas:

Browser
El usuario accede a localhost:3000/api/message
Middleware
Intercepta y loguea la request antes de continuar.
Route
Identifica el endpoint y lo redirige al controller correcto.
Controller
Recibe la request y llama a WelcomeService.
Service
Construye el mensaje usando el tipo WelcomeMessage.
Model
Define la forma del dato: title, subtitle, timestamp…
Response
El controller responde con JSON al navegador.
¿Por qué usarla?

Los beneficios reales

No es burocracia. Cada capa resuelve un problema concreto.

🧹
Mantenible
Sabes exactamente dónde está cada cosa. Nuevos devs entienden el proyecto en minutos.
🧪
Testeable
Los services son funciones puras. Los puedes testear sin levantar Express.
📦
Escalable
Agregar un nuevo módulo (users, products…) es copiar la misma estructura.
🔄
Flexible
Cambias Express por Fastify tocando solo routes y controllers. El negocio queda intacto.
👥
Colaborativa
Varios devs pueden trabajar en capas distintas sin pisarse el código.
🛡️
Robusta
El bajo acoplamiento hace que los bugs no se propaguen entre capas.
